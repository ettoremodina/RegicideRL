# Repository structure

The repository separates game rules from interfaces, agents, experiment
orchestration, and generated artifacts. Imports generally point inward toward
the rules engine: clients and agents may use `game/`, while `game/` does not
depend on a UI or a learning framework.

## Source map

```text
Regicide/
|-- game/                  Core rules, state transitions, and action encoding
|-- agents/                Common agent API and implemented policies
|-- solvers/               Gymnasium adapter and solver workflows
|-- ui/                    Pygame desktop client
|-- control_panel/         Local browser control panel
|-- ml_logger/             Reusable run and telemetry package
|-- integrations/          Regicide-specific logging adapter
|-- scripts/               User-facing utilities and report pipeline
|-- tests/                 Rules, agents, logging, UI, and documentation tests
|-- docs/                  Curated guides, report site, and generated API pages
|-- rules/                 Reference rulebook material
|-- artifacts/             Generated runs, datasets, reports, and models
|-- config.yaml            Solver and experimental-report configuration
|-- config_test.yaml       Small workloads for legacy development experiments
|-- logger_config.yaml     Logging, telemetry, and artifact configuration
|-- benchmark.py           Rules/environment throughput entry point
|-- control_panel.pyw      Windows launcher for the local control panel
`-- requirements.txt       Runtime and research dependencies
```

## Core game layer

`game/regicide.py` owns the mutable game state and official rule transitions.
`game/action_handler.py` derives phase-specific legal actions, while
`game/action_space.py` maps those choices into stable global action identifiers.
This boundary lets the UI, scripted agents, and Gymnasium environment share one
legality model instead of implementing rules independently.

## Agents and solvers

`agents/base_agent.py` defines the policy interface. The publication comparison
uses:

- `random_agent.py` as the legal-action baseline;
- `heuristic_agent.py` as the hand-authored rule-based policy;
- `pimc_agent.py` for determinization with independent rollouts;
- `ismcts_agent.py` for tree search across sampled information sets.

`agents/determinize.py` contains hidden-state sampling shared by the search
agents. `agents/ismcts_trace.py` records one ISMCTS decision as replayable data
for the [decision visualizer](ISMCTS_VISUALIZER.md); it is inert unless a tracer
is explicitly attached to the agent. PPO and AlphaZero adapters remain in this package to preserve the
research history, but they are not required by the final release.

`solvers/env.py` exposes the game through Gymnasium. The remaining `solvers/`
modules cover evaluation, multiprocessing, PPO and behavioral-cloning
experiments, model analysis, and the unfinished AlphaZero workflow. These
modules consume the core rules; they are not alternate rules engines.

## User interfaces

`ui/pygame_app.py` is the interactive desktop game. `ui/__main__.py` makes it
available as `python -m ui`.

`control_panel/` is a local web application with a fixed command registry,
validated configuration editing, subprocess tracking, and artifact browsing.
`control_panel/__main__.py` provides `python -m control_panel`; the Windows
`control_panel.pyw` launcher starts the same application without a console.
Static browser assets live under `control_panel/static/`.

## Runs, logging, and reports

`ml_logger/` is a reusable, domain-neutral package for run lifecycle, structured
events, metrics, telemetry, and portable reports. `integrations/regicide_logging.py`
adds game-history recording without coupling the logger to Regicide.

User-facing utilities live under `scripts/`:

- `log_game.py` records a random game;
- `runs.py` inspects and replays catalog entries;
- `analyze_runs.py` aggregates game summaries;
- `experimental_report/` runs paired agent comparisons and analyzes them;
- `generate_docs.py` builds the pdoc reference into `docs/api/`;
- `trace_ismcts.py` records an ISMCTS decision and renders
  `docs/ismcts_visualizer.html` from the template in `scripts/templates/`;
- `migrate_artifacts.py` imports outputs from the older directory layout.

The `artifacts/` directory is generated state, not source code. A typical run is
organized as follows:

```text
artifacts/runs/<date>/<run_id>/
|-- manifest.json
|-- config.yaml
|-- logs/
|-- metrics/
|-- games/
|-- datasets/
|-- models/
|-- checkpoints/
`-- analysis/
```

Only folders used by a particular command need to exist. Reproducible reports
keep their effective configuration and raw datasets inside the run directory.

## Documentation layout

- `docs/site/` is the hand-authored, navigable project and results website.
- `docs/USAGE.md` contains operational commands.
- `docs/DOCUMENTATION.md` defines the API docstring policy.
- `docs/api/` is generated by pdoc and can be rebuilt at any time.
- `docs/planning/` contains historical plans and should not be read as the
  current release contract.
